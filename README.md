# 🚀 GitHub Repository Summarizer API

> FastAPI service that analyzes any public GitHub repository and returns a structured, human‑readable summary generated by an LLM.

---

## ✨ Overview

This service accepts a GitHub repository URL and returns:

- project purpose
- main technologies
- architecture structure

It intelligently selects relevant files, filters noise, manages context limits, and uses an LLM to produce a structured summary.

Designed as an **LLM‑powered codebase understanding system**, not just a text generator.

---

## 🧠 Problem This Solves

Repositories are complex:

- hundreds of files
- nested dependencies
- mixed languages
- configs + source + docs

Sending everything to an LLM is impossible because of context limits, latency, cost, and noise. This service solves that by implementing a **selective repo intelligence pipeline**.

## 📦 API Endpoint

### POST `/summarize`

**Request**

```json
{
  "github_url": "https://github.com/psf/requests"
}
```

**Response**

```json
{
  "summary": "Requests is a Python HTTP library...",
  "technologies": ["Python", "urllib3", "certifi"],
  "structure": "Source code in src/requests/, tests in tests/, docs in docs/"
}
```

**Error response**

```json
{
  "status": "error",
  "message": "Description of what went wrong"
}
```

## 🚀 Quick Start

### 1 — Unzip and enter the folder

```bash
cd repo-summarizer
```

### 2 — Create environment

```bash
python -m venv venv
source venv/bin/activate
```

Windows:

```bash
venv\Scripts\activate
```

### 3 — Install dependencies

```bash
pip install -r requirements.txt
```

### 4 — Set API key

```bash
export NEBIUS_API_KEY=your_nebius_key
```

Optionally set a GitHub token to avoid rate limits:

```bash
export GITHUB_TOKEN=your_github_token
```

### 5 — Run server

```bash
uvicorn main:app --host 0.0.0.0 --port 8000
```

### 6 — Test request

```bash
curl -X POST http://localhost:8000/summarize \
  -H "Content-Type: application/json" \
  -d '{"github_url": "https://github.com/psf/requests"}'
```

### Interactive Docs

Open in browser:

```
http://localhost:8000/docs
```

## 🏆 Final Production Benchmark (Head-to-Head)

While multiple **model families** were considered during development (Qwen, DeepSeek, GLM, Kimi, Llama, Hermes), the **final decision** was made after a direct comparison between the two strongest candidates available in Nebius Token Factory:

| Model | Type |
|------|------|
| **Qwen/Qwen3-Coder-480B-A35B-Instruct** | Code-specialist model |
| **Meta/Llama-3.3-70B-Instruct** | General reasoning model |

### 📊 Head-to-Head Evaluation Results

**Test repository:** `Yorko/mlcourse.ai`  
**Task:** structured repository summarization (summary + technologies + structure)

| Criterion | Qwen3-Coder-480B | Llama-3.3-70B |
|---|---:|---:|
| Architecture inference | 10 | 7 |
| Technology detection | 10 | 8 |
| Structural accuracy | 10 | 7 |
| Noise filtering | 9 | 8 |
| Semantic completeness | 10 | 7 |
| **Total** | **49 / 50** | **37 / 50** |


**Meta/Llama-3.3-70B-Instruct** is a strong general model, but not specialized for repo-level reasoning — it missed fine-grained structural signals that Qwen-Coder captured correctly.

✅ **Production model:** `Qwen/Qwen3-Coder-480B-A35B-Instruct`

## 🧪 Repository Processing Strategy

### Included (priority order)

1. **README + config files** (`pyproject.toml`, `package.json`, `go.mod`, etc.) → project intent and dependencies
2. **Entry-point files** (`main.py`, `app.py`, `index.js`, etc.) → runtime logic
3. **Source code files** (`.py`, `.js`, `.ts`, `.go`, `.rs`, etc.) → functionality
4. **Config files** (`.yaml`, `.toml`, `.json`, `.cfg`) → environment and settings

### Skipped

- **Binary and media files** — images, fonts, audio/video, compiled code (`.pyc`, `.class`, `.exe`, etc.)
- **Lock files** — `package-lock.json`, `yarn.lock`, `poetry.lock`, etc. — redundant with manifest files
- **Build artifacts and caches** — `node_modules/`, `dist/`, `build/`, `__pycache__/`, `.venv/`
- **Hidden files** — `.gitignore`, `.editorconfig`, `.ds_store`, etc.

Reason: they add tokens but no semantic signal.

### Context Management

| Rule | Value |
|------|-------|
| Total chars | 60,000 max |
| Per file | 5,000 max |
| Ordering | Priority-sorted (most informative first) |
| Truncation | Enabled — `... [truncated]` marker |

Result: **Most informative files are always included, even for large repos.**

## 🛡 Error Handling

Handles all edge cases with appropriate HTTP status codes:

| Case | HTTP Code |
|------|-----------|
| Invalid GitHub URL | 400 |
| Repository not found | 404 |
| Private repo / rate limit | 404 |
| No readable files | 422 |
| GitHub API failure | 502 |
| LLM error | 500 |

Returns structured error:

```json
{
  "status": "error",
  "message": "Description of what went wrong"
}
```
