# 🚀 GitHub Repository Summarizer API

> Production‑grade FastAPI service that analyzes any public GitHub repository and returns a structured, human‑readable summary generated by an LLM.

---

## ✨ Overview

This service accepts a GitHub repository URL and returns:

- project purpose
- main technologies
- architecture structure

It intelligently selects relevant files, filters noise, manages context limits, and uses an LLM to produce a structured summary.

Designed as an **LLM‑powered codebase understanding system**, not just a text generator.

---

## 🧠 Problem This Solves

Repositories are complex:

- hundreds of files  
- nested dependencies  
- mixed languages  
- configs + source + docs  

Sending everything to an LLM is impossible because of context limits, latency, cost, and noise. This service solves that by implementing a **selective repo intelligence pipeline**.

## 📦 API Endpoint

### POST `/summarize`

**Request**

```json
{
  "github_url": "https://github.com/psf/requests"
}
```

**Response**

```json
{
  "summary": "Requests is a Python HTTP library...",
  "technologies": ["Python", "urllib3"],
  "structure": "Source code in requests/, tests in tests/, docs in docs/"
}
```

### 1 — Clone project

```bash

```

### 2 — Create environment

```bash
python -m venv venv
source venv/bin/activate
```




## 🧪 Repository Processing Strategy

### Included (priority order)

1. README + config files → project intent  
2. Entrypoints → runtime logic  
3. Source files → functionality  
4. Configs → dependencies  

### Skipped

- binaries
- lock files
- caches
- build artifacts
- media
- hidden system files

Reason: they add tokens but no semantic signal.

### Context Management Strategy

To avoid LLM overflow:

| Rule        | Value            |
|-------------|------------------|
| Total chars | 60k max          |
| Per file    | 5k max           |
| Ordering    | priority-sorted  |
| Truncation  | enabled          |

Result: **Most informative files are always included.**
